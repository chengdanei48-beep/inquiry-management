# 要件定義書

## 1. 目的・背景

社内ヘルプデスクに寄せられる問い合わせを一元的に記録・管理し、**対応実績を集計・分析できる**ようにするアプリを作成する。

- 題材の選定理由は [selection-rationale.md](selection-rationale.md) を参照。
- 分野を社内ヘルプデスクとした理由は次のとおり。
  - 依頼者も担当者も社員で完結し、顧客マスタや個人情報の公開範囲といった論点が増えない。
  - カテゴリ(PC不具合、アカウント、備品申請など)とステータスが明確で、集計結果に意味が出る。
  - 「どのカテゴリが多いか」「どこで対応が滞っているか」を、改善の判断材料として説明しやすい。

### 決定事項

| 項目 | 内容 |
|---|---|
| 分野 | 社内ヘルプデスク(社員 → 情報システム部・総務・人事への問い合わせ) |
| 種類 | フォーム入力の単一チャネル(Web画面から手入力で登録し、カテゴリで分類) |
| 用途 | 対応実績の分析・集計を重視 |

## 2. 対象範囲

### スコープ内
- 問い合わせの登録・一覧・詳細表示・検索/絞り込み
- ステータス変更、担当者の割当、対応履歴の記録
- 社員マスタ、カテゴリマスタの管理
- 対応実績の集計・表示

### スコープ外
- メール、電話、チャットなど外部チャネルとの連携(受付チャネルはフォーム入力のみ)
- 外部への通知(メール送信、Slack 連携など)
- 依頼者本人が投稿する公開フォーム
- 本格的な認証・権限管理(ログイン画面、パスワード管理)
- クラウド環境・外部サービスの利用

## 3. 利用者と役割

| 役割 | 内容 |
|---|---|
| 対応担当者 | ヘルプデスクの担当社員。問い合わせの登録、ステータス変更、対応記録、集計の閲覧を行う |
| 依頼者 | 問い合わせを行った社員。システムの操作者ではなく、社員マスタ上のデータとして登録される |

認証は行わず、画面上で「操作する担当者」を選択する簡易方式とする。履歴にはその担当者名を記録する。

## 4. 業務フロー

1. 依頼者から連絡を受けた担当者が、問い合わせをフォームから登録する(状態: 未対応)。
2. 担当者を割り当て、対応を開始する(状態: 対応中)。
3. 回答待ちなどで止まる場合は保留にする(状態: 保留)。
4. 解決したら完了にする(状態: 完了)。完了後に再開が必要な場合は対応中に戻せる。
5. 各操作は対応履歴として残り、蓄積したデータを集計画面で確認する。

### ステータス遷移

```
未対応 → 対応中 ⇄ 保留
          ↓
         完了 → 対応中(再開)
```

## 5. 機能要件

### 5.1 問い合わせ管理

| ID | 機能 | 概要 |
|---|---|---|
| F-01 | 問い合わせ登録 | 件名、内容、依頼者(社員)、カテゴリ、優先度を入力して登録する。登録時のステータスは「未対応」 |
| F-02 | 問い合わせ一覧 | 一覧表示。ステータス、カテゴリ、担当者、依頼者の部署で絞り込み、件名・内容のキーワード検索ができる |
| F-03 | 問い合わせ詳細 | 内容と対応履歴を時系列で表示する |
| F-04 | ステータス変更 | 4章の遷移に従って変更する。不正な遷移は拒否する |
| F-05 | 担当者割当 | 担当者を割り当てる/変更する |
| F-06 | 対応履歴の記録 | ステータス変更・担当者変更・コメント追加を、日時と操作した担当者とともに記録する |
| F-07 | 問い合わせ編集 | 件名、内容、カテゴリ、優先度を修正できる(修正も履歴に残す) |

### 5.2 マスタ管理

| ID | 機能 | 概要 |
|---|---|---|
| F-08 | 社員マスタ | 氏名、部署、担当者区分(担当者かどうか)の登録・編集 |
| F-09 | カテゴリマスタ | カテゴリの登録・編集。初期値として「PC・ネットワーク」「アカウント・権限」「備品・ソフト申請」「入退社手続き」「その他」を用意する |

### 5.3 集計・分析

集計期間(開始日〜終了日)を指定して表示する。

| ID | 集計 | 内容 |
|---|---|---|
| A-01 | カテゴリ別件数 | 期間内の受付件数をカテゴリ別に集計する |
| A-02 | 部署別件数 | 依頼者の部署別に受付件数を集計する |
| A-03 | カテゴリ別平均対応時間 | 受付から完了までの平均時間をカテゴリ別に集計する(完了済みのみ対象) |
| A-04 | 担当者別処理件数 | 担当者ごとの完了件数と、未完了件数を集計する |
| A-05 | 月別受付件数の推移 | 月ごとの受付件数を表示する |
| A-06 | ステータス別件数 | 現在のステータスごとの件数を表示する |

集計の定義:
- **受付日時**: 問い合わせの登録日時。
- **対応時間**: 受付日時から、最後に「完了」にした日時までの経過時間。再開した場合は最終の完了時点を使う。
- **対象期間**: 受付日時が期間内の問い合わせを対象とする。

## 6. データ要件

データは SQLite(ファイルDB)に保存する。DBファイルは Git に含めない。

| テーブル | 主な項目 |
|---|---|
| employees(社員) | id、氏名、部署、担当者区分、有効フラグ |
| categories(カテゴリ) | id、名称、表示順、有効フラグ |
| inquiries(問い合わせ) | id、件名、内容、依頼者ID、カテゴリID、優先度、ステータス、担当者ID、受付日時、更新日時、完了日時 |
| inquiry_histories(対応履歴) | id、問い合わせID、種別(ステータス変更/担当者変更/コメント/編集)、内容、操作者ID、日時 |

- 優先度は「高」「中」「低」の3段階とする。
- 社員・カテゴリは、過去の問い合わせから参照されるため物理削除せず、無効化で扱う。

## 7. 非機能要件

| 区分 | 内容 |
|---|---|
| 動作環境 | ローカルのみで動作する。クラウド・有料サービスは使わない |
| 技術 | Node.js v24 以降、標準の `node:sqlite`、HTML / 素のJavaScript。依存は標準モジュールを優先し、追加する場合は無料のOSSに限る |
| ポート | アプリの既定ポートは 8080 |
| 性能 | 数千件規模の問い合わせで、一覧・集計が体感で待たされない(目安: 1秒以内) |
| 入力検証 | 必須項目、文字数、存在しないIDを検証し、画面とAPIの両方でエラーを返す |
| 安全性 | SQLはプレースホルダを使う。画面出力時は入力値をエスケープする |
| データ保護 | 個人情報は氏名・部署に限定する。DBファイルをリポジトリに含めない |
| 保守性 | `npm test` で自動テストが実行できる |

## 8. 受け入れ条件

- F-01〜F-09 の各機能が画面から操作できる。
- 4章に反する不正なステータス遷移は、画面・APIとも拒否される。
- A-01〜A-06 の集計が、テストデータの手計算の結果と一致する。
- すべての変更操作が対応履歴に残る。
- `npm test` が通る。
- ポート 8080 で起動し、`http://localhost:8080/` で応答する。

## 9. 未決事項

| 項目 | 内容 |
|---|---|
| 営業時間の扱い | 対応時間を単純な経過時間とするか、営業時間のみで数えるか |
| 保留の扱い | 保留中の時間を対応時間から除くか |
| 初期データ | 社員マスタのサンプルデータをどの程度用意するか |
| 集計の表示形式 | 表のみとするか、簡易なグラフも付けるか |
| CSV出力 | 集計結果や一覧のCSV出力を対象にするか |
| 入力の文字数上限 | 件名・内容・コメントの上限値(設計書で確定する) |
