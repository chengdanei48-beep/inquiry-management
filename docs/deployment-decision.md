# 判断記録: コンテナ化・デプロイは行わない

| 項目 | 内容 |
|---|---|
| 日付 | 2026/10/12 |
| 問い | コンテナ化(Docker など)やデプロイは必要か |
| 結論 | **必要ない。行わない。** ローカルで `npm start` するだけで使う |
| 見直す条件 | 「環境差をなくしたい」「提出物に含めたい」など、具体的な要望が出たとき(下記「コンテナ化が必要になる場面」) |

## 結論の理由

| 観点 | 現在の決定 | コンテナ化・デプロイとの関係 |
|---|---|---|
| 課金ルール([CLAUDE.md](../CLAUDE.md)) | クラウド・有料サービスは使わず、ローカルだけで動作する | クラウドへのデプロイは、ルールに反する |
| 公開範囲([要件定義書](requirements.md) 7章) | `localhost` のみで待ち受ける。認証を持たないため、外部には公開しない | 外部に出す構成にすると、前提が崩れる |
| 利用形態 | 1台のマシンで、少人数が使う想定 | 複数台・スケールの必要がない |
| 導入の手間 | Node.js 24 と `npm start` だけ(依存パッケージなし) | コンテナを入れるほうが、手順が増える |

課題の説明では、`npm run seed` → `npm start` の2コマンドで再現できる点が強みになる。

## このままデプロイすると困ること(意図的に対象外としている)

社内サーバーなどへ載せる場合に、次が未対応である。いずれも、ローカル利用の前提のため、課題の範囲外としている。

| 未対応の点 | 内容 |
|---|---|
| 認証 | 「操作する担当者」は、選ぶだけの簡易方式。外部に出すと、誰でも操作できる |
| 待ち受けアドレス | `127.0.0.1` 固定。Host ヘッダーも localhost のみ許可している |
| 通信の暗号化 | HTTP のみ。HTTPS はない |
| バックアップ | 手動(README「バックアップと復元」)。自動バックアップはない |
| 同時接続・スケール | SQLite は1プロセス前提。複数台での負荷分散はできない |

## コンテナ化が必要になる場面と、必要な変更

次の場合は、コンテナ化を検討する。

- 利用する環境に Node.js 24 を入れられない、など、環境差をなくしたいとき
- 提出物の再現性を高めたいとき

そのときに必要な変更は、次のとおり(現時点では実施していない)。

1. **待ち受けアドレスを設定可能にする**: 現在は `127.0.0.1` 固定のため、コンテナ内では、ホストから届かない。`HOST` 環境変数を追加し、コンテナ内は `0.0.0.0` にする。設計書(api-design.md 3章の設定、requirements.md 7章)も更新する。
2. **ホスト側の公開を制限する**: `-p 127.0.0.1:8080:8080` のように、ホストでも localhost のみに公開する。認証がないため、これは必須。
3. **データの永続化**: `data/` をボリュームにする(DBと月次集計ファイル)。
4. **Dockerfile**: `node:24-slim` を基にする。依存パッケージがないため、ファイルのコピーと `CMD ["npm", "start"]` のみで足りる。

## 注意

- Docker 自体は、個人・教育用途では無料だが、企業での利用には有償ライセンスが必要になる場合がある。「課金が発生する技術・サービスは使わない」というルール([CLAUDE.md](../CLAUDE.md))に照らして、導入前に確認する。
- 認証を設けずに、コンテナを外部へ公開しない。
