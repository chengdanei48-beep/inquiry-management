# InquiryManagement(問い合わせ管理)

[![version](https://img.shields.io/badge/version-1.1.0-blue)](CHANGELOG.md) [![license](https://img.shields.io/badge/license-MIT-green)](LICENSE)

社内ヘルプデスクに寄せられる問い合わせを、登録・一覧・ステータス管理・担当者割当・履歴で管理し、対応実績を集計・分析するアプリ。課題として作成した。

## 特徴

- 問い合わせの登録・検索・絞り込み・ステータス変更(未対応 → 対応中 ⇄ 保留 → 完了)・担当者割当・コメント・履歴
- 対応実績の集計(カテゴリ別・部署別・平均対応時間・担当者別・月別・ステータス別)を、表とグラフで表示。CSV 出力、月ごとのファイル保存
- 対応時間は、平日 9:00〜18:00 のみを数え、保留の期間を除く
- 複数の担当者が同時に更新しても、先に更新された内容を黙って上書きしない(409 で再読み込みを促す)

## 技術スタック

- Node.js v24 以降(標準の `node:sqlite` を使用)
- SQLite(ファイル DB)
- HTML / 素のJavaScript(ブラウザは Chrome(最新版)を想定)

課金が発生する技術・サービスは使わず、ローカルだけで動作する(課題の提出要件のため、AWS の EC2 1 台へのデプロイ手順を用意している: [docs/aws-deployment.md](docs/aws-deployment.md))。npm の依存パッケージは無い。

## 起動とテスト

```
npm start        # http://localhost:8080/ で起動(localhost のみ)
npm run seed     # サンプルデータ(社員10名、問い合わせ15件)を投入。既にデータがあれば何もしない
npm test         # 自動テスト
npm run e2e      # 実際の Chrome で、全画面の操作を自動確認する(下記)
```

### 初めて使うとき

1. `npm start` で起動し、ブラウザで http://localhost:8080/ を開く。
2. サンプルデータで試すときは、起動する前に `npm run seed` を実行する。
3. サンプルデータを使わないときは、「マスタ管理」で最初の担当者(担当者区分)を追加する。追加した担当者は「操作する担当者」に自動で設定される(担当者がいない間だけ、操作者なしで追加できる)。
4. 画面右上の「操作する担当者」を選ぶと、登録・変更ができる(選択はブラウザに保存される)。

初回起動時に、DBとテーブル、カテゴリの初期値(5種)を自動で作成する。

### 設定(環境変数)

| 変数 | 既定 | 内容 |
|---|---|---|
| `PORT` | `8080` | 待ち受けるポート |
| `HOST` | `127.0.0.1` | 待ち受けるアドレス。既定は localhost のみ。外部に公開するときだけ `0.0.0.0` を指定する(**`APP_PASSWORD` が無いと起動しない**) |
| `APP_PASSWORD` | (なし) | 認証(Basic 認証)のパスワード(12 文字以上)。設定すると、全ての画面・API で認証を求める。`HOST` が localhost 以外のときは必須 |
| `APP_USER` | `admin` | 認証のユーザー名 |
| `ALLOWED_HOSTS` | (なし) | localhost 以外で受け付ける Host 名(カンマ区切り。`*` で全て)。外部に公開するときに指定する |
| `DB_PATH` | `data/inquiry.db` | DBファイルの場所。月次集計の保存先は、このファイルと同じディレクトリの `reports/`(既定は `data/reports/YYYY-MM/`) |

`data/` は Git に含めない。

### バックアップと復元

DBファイルを、手動でコピーする。自動バックアップはしない。

1. **サーバーを停止する**(`Ctrl+C`)。
2. `data/inquiry.db` を、別の場所にコピーする(`data/reports/` の月次集計も残す場合は、`data/reports/` もコピーする)。
3. **復元**するときは、サーバーを停止して、コピーしたファイルを `data/inquiry.db` として戻し、`npm start` で起動する。

DBのスキーマの版(`PRAGMA user_version`)が、このアプリより新しいDBは、開かない(誤って壊さないため)。

### 実際の Chrome での確認(`npm run e2e`)

Chrome を操作して、全画面の操作・入力検証・エラー表示・キーボード操作・XSS・初期セットアップを確認する(約100項目)。

- 一時ディレクトリのDBで、アプリの既定ポート(8080)にサーバーを起動して確認する。8080 が使用中のときは、実行せずに案内して終了する(他のプロセスは停止しない)。
- Chrome が見つからないときは、案内して終了する。`CHROME_PATH` 環境変数で、Chrome の実行ファイルを指定できる。
- スクリーンショットは `e2e-output/` に保存される(Git には含めない)。

## 利用上の注意

- 既定では、サーバーは `localhost` のみで待ち受け、認証を持たない。**「操作する担当者」は、選ぶだけの簡易方式**で、なりすましを防げない。
- 外部に公開する(AWS へのデプロイ)ときは、共通のパスワード(Basic 認証)を必須とし、**パスワードが無いと起動しない**。ただし、通信は HTTP のままで、ユーザーごとの認証・総当たり対策・自動バックアップはない。**サンプルデータだけ**を入れ、実データは入れない(制限と、本番で必要な対策は [判断記録](docs/deployment-decision.md))。
- コンテナ化は、行っていない。

## 公開版について

この公開リポジトリには、開発用の非公開リポジトリの**コミット履歴**を含めている。個人のメールアドレスは公開しないため、コミットの作者のメールアドレスは、GitHub の noreply のアドレスに置き換えてある(そのため、コミットの ID は、非公開リポジトリのものと異なる)。開発は、Issue → 専用ブランチ → プルリクエストの流れで行った。コミットメッセージやマージコミットにある `#番号` は、非公開リポジトリの Issue・PR の番号で、その経緯(Issue・PR)は非公開リポジトリにある。

## 公開版の更新(開発者向け)

開発用(非公開)リポジトリの履歴を、個人のメールアドレス・名前を隠して、公開リポジトリへ反映する。

```
npm run publish:public               # 試し実行(検証だけ。何も反映しない)
npm run publish:public -- --push     # 公開リポジトリへ反映する
```

- 作業用のクローンで、作者・コミッターのメールを GitHub の noreply に置き換え、名前をアカウント名に統一した履歴を作る(日時・内容・メッセージは変えない)。個人情報は、スクリプトに書かず、履歴から自動で検出する。
- 反映前に、次を検証する: 作者欄に noreply 以外が無い / コミット数と最新の内容が開発用と一致 / 検出した元のメール・名前が、**全履歴のメタデータと全ファイルの内容**に残っていない / `npm test`(`--skip-tests` で省略可)。1つでも満たさなければ、反映しない。
- 同じ置き換えを繰り返すため、コミットの ID は変わらず、公開側には**通常の push(fast-forward)**で追加される。公開側と食い違う場合は、`--force` を付けない限り中止する。
- 実行前に、作業ツリーがきれいで、`master` が `origin/master` と一致している必要がある。
- GitHub CLI(`gh`)でログインしている必要がある(公開する作者名・noreply のメールは、アカウント情報から作る)。環境変数 `PUBLISH_PUBLIC_URL`・`PUBLISH_NAME`・`PUBLISH_EMAIL` で指定もできる。
