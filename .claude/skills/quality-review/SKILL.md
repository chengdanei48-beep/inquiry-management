# 品質レビュー(quality-review)

機能追加・修正の PR を出す前や、定期的な全体点検で使うチェックリスト。
**ドキュメント(`docs/`)を正として**実装を直す。ただし docs に無い実在機能は、docs 側に追記する。

## 手順

1. 下記「自動チェック」を実行し、全て通す。
2. 「観点チェックリスト」を、変更した範囲について点検し、指摘を `ファイル:行` つきでまとめる。
3. 「docs ⇔ 実装の差異」を確認する。差異は docs を正として実装を直す(docs に無い実在機能は docs へ追記)。
4. 修正は Issue → 専用ブランチ → PR(CLAUDE.md の開発フロー)で行う。動作確認のサーバー起動は CLAUDE.md のポート規約に従う。

## 自動チェック

```
npm test    # node --test(Node.js 標準のテストランナー)
```

## 観点チェックリスト

### サーバー(Node.js / SQLite)

- 入力検証: 受け取った値(件名・本文・ステータス等)の型・長さ・許容値をサーバー側で検証している。クライアントの検証に頼らない。
- SQL: 値は**プレースホルダ(`?`)**で渡し、文字列連結で SQL を組み立てていない。LIKE のワイルドカードをエスケープ。
- エラー応答: 形式を統一し、ステータスコード(400/404/409/500)を使い分ける。内部情報(スタックトレース・SQL)を返さない。
- HTTP: 作成は 201。存在しない ID は 404。想定外の例外で落ちず、500 を返す。
- トランザクション: 複数テーブルを更新する処理(問い合わせ + 履歴など)は 1 トランザクションにまとめる。
- 設定: ポート・DB ファイルのパスは環境変数で上書きできる。DB ファイル(`*.db`)は Git に入れない。
- テスト: 正常系だけでなく、境界値(文字数上限)・存在しない ID(404)・不正な入力(400)を確認している。

### 画面(HTML / JavaScript)

- XSS: ユーザー入力を `innerHTML` に入れない(`textContent` を使う)。
- エラー処理: ユーザーに内部情報(URL・ステータスコード等)を見せない。通信失敗とデータ無しを区別する。
- アクセシビリティ: フォーム項目に `label`、入力エラーに `role="alert"` と `aria-invalid`。色だけで情報を伝えない。
- 依存: 外部の CDN・有料サービスを使っていない(CLAUDE.md の課金ルール)。

### 課金ルール

- `package.json` の依存が全て無料のオープンソースである。有料 API を使っていない。クラウドは、課題の提出要件(AWS の EC2 1 台。docs/aws-deployment.md)に限る。
- 外部に公開する設定(`HOST` が localhost 以外)で、認証(`APP_PASSWORD`)なしでは起動しない。AWS の認証情報・パスワードがリポジトリに無い。

### docs ⇔ 実装の差異(docs を正とする)

`docs/` の要件定義・画面設計・API・DB 定義と実装を突き合わせる。

- 画面の文言(ボタン・見出し・必須表示)、表示形式(日付 `YYYY/MM/DD` 等)。
- 入力制限(文字数・許容値)と、エラー表示の仕様。
- API(パス・フィールド・ステータスコード・クエリパラメータ)と DB 定義(型・長さ・制約)。
- docs 同士の整合(参照している要件定義書のバージョン、ER 図とテーブル定義)。
- 新機能を入れたら docs(要件・画面設計・ER図・README)を同じ PR で更新する。
